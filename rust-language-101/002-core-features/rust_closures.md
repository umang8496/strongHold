## 1. Mental Model & Core Concepts

In Rust, a **closure** is an anonymous function that can **capture variables from the scope in which it is defined**.  

### How Closures Differ from Functions (`fn`)

- **Functions (`fn`)**: Static, named items. They have access only to their own parameters, local bindings, and global constants/statics.  
  They cannot capture arbitrary local variables from an outer lexical scope.
- **Closures**: Ephemeral, anonymous values. They bundle executable code **together with captured state** from their environment.

### The Mental Anchor

In languages with a garbage collector (JavaScript, Python, Go), closures implicitly hold references to variables on the heap or manage scope reference-counting invisibly.  

In Rust, **a closure is simply an anonymous struct generated by the compiler**.  
Each captured variable becomes a field inside that struct, and the borrow checker enforces strict ownership and lifetime rules on those fields.

## 2. Syntax & Basic Usage

Rust uses pipe characters `|...|` to enclose closure parameters.

```rust
// 1. Standard function
fn add_one_v1(x: u32) -> u32 {
    x + 1
}

// 2. Fully annotated closure
let add_one_v2 = |x: u32| -> u32 { x + 1 };

// 3. Type inference (braces optional for single expressions)
let add_one_v3 = |x| x + 1;
```

### Type Inference Rules

Closures infer argument and return types from context.  
However, once an argument type is inferred from its first use, that closure's signature is **locked**:

```rust
let identity = |x| x;

let _s = identity(String::from("hello")); // Locks identity to: Fn(String) -> String
// let _n = identity(5);                 // ERROR: expected struct `String`, found integer
```

## 3. Capturing the Environment (The 3 Modes)

When a closure reads or writes a variable from its outer scope,  
the compiler automatically chooses the **least restrictive capture mode** necessary to make the closure's body compile:

| Mode                     | Captured Form   | Mental Model           | Rust Mechanism            |
| :----------------------- | :-------------- | :--------------------- | :------------------------ |
| **By Reference**         | `&T`            | Read-only access       | Immutable borrow          |
| **By Mutable Reference** | `&mut T`        | Read & write access    | Exclusive mutable borrow  |
| **By Value / Ownership** | `T`             | Consumption / transfer | Move / drop               |

### Example 1: Capture by Reference (`&T`)

```rust
let greeting = String::from("Hello");

// Only reads `greeting`; captures `&greeting`
let print_greeting = || println!("{}", greeting);

print_greeting();
println!("Can still read greeting: {}", greeting); // OK: borrowed immutably
```

### Example 2: Capture by Mutable Reference (`&mut T`)

```rust
let mut counter = 0;

// Mutates `counter`; captures `&mut counter`
let mut increment = || {
    counter += 1;
    println!("Counter is now {}", counter);
};

increment();
increment();

// println!("{}", counter); // OK here, because `increment` is not called again afterwards
```

### Example 3: Capture by Value (`T`)

```rust
let data = vec![1, 2, 3];

// Consumes `data` by passing it to `drop` or another consuming function
let consume_data = || {
    let _owned = data; // Ownership transferred into `_owned`
};

consume_data();
// println!("{:?}", data); // ERROR: value used here after move
```

## 4. The `move` Keyword

By default, the compiler infers whether to capture by `&T`, `&mut T`, or `T`.  
Placing `move` before the pipes forces the closure to **take ownership** of all variables it uses, moving (or copying, if types implement `Copy`) them into the closure.

```rust
let numbers = vec![1, 2, 3];

// Forced ownership transfer into the closure
let print_numbers = move || {
    println!("{:?}", numbers);
};

// println!("{:?}", numbers); // ERROR: borrow of moved value: `numbers`
```

### When is `move` Essential?

1. **Multi-threading**: Passing closures to `std::thread::spawn` requires `'static` data because the thread may outlive the creating scope.  
2. **Returning closures**: If a closure references local variables, returning it without `move` produces a dangling reference error.

```rust
use std::thread;

let list = vec![10, 20, 30];

// The thread requires that closure captures have 'static lifetimes.
// Without `move`, the closure would borrow `list` from the main thread frame.
thread::spawn(move || {
    println!("Thread data: {:?}", list);
}).join().unwrap();
```

## 5. Disjoint Capture (Rust 2021+)

Prior to Rust 2021, if a closure accessed a single field of a struct, the **entire struct** was captured.  

Starting in Rust 2021, the compiler analyzes closures at the **field level** (disjoint capture).  
It captures only the specific fields actually referenced:

```rust
struct User {
    name: String,
    age: u32,
}

let mut user = User {
    name: String::from("Ferris"),
    age: 10,
};

// Captures `&mut user.age` and `&user.name` separately
let mut celebrate = || {
    println!("Happy Birthday, {}!", user.name); // &user.name
    user.age += 1;                             // &mut user.age
};

celebrate();
```

> **Warning with `move`**: When `move` is used, Rust 2021 moves only the accessed fields.  
> If you later need the entire struct intact or implement `Drop`, be mindful that the remaining fields may stay in the outer scope, while consumed fields are gone.

## 6. Behind the Curtain: Compiler Desugaring

To master Rust closures, understand how the compiler desugars them into ordinary structs.

### What You Write:

```rust
let prefix = String::from("Log: ");
let mut count = 0;

let mut logger = |msg: &str| {
    count += 1;
    println!("{}{}: {}", prefix, count, msg);
};

logger("Init");
```

### What the Compiler Emits (Conceptual):

```rust
// 1. An anonymous struct holding the captured environment
struct ClosureEnvironment<'a> {
    prefix: &'a String,
    count: &'a mut usize,
}

// 2. Trait implementation for that struct
impl<'a> FnMut<(&str,)> for ClosureEnvironment<'a> {
    extern "rust-call" fn call_mut(&mut self, (msg,): (&str,)) {
        *self.count += 1;
        println!("{}{}: {}", self.prefix, *self.count, msg);
    }
}

// 3. Instantiation
let mut logger = ClosureEnvironment {
    prefix: &prefix,
    count: &mut count,
};
```

Because every closure has a unique, unnameable type generated by the compiler, **no two closures share the same type**, even if they possess identical signatures.

## 7. The Closure Trait Hierarchy (`Fn`, `FnMut`, `FnOnce`)

Rust defines three traits that closures can implement. They describe how the closure may be called and what it does with its captured state:

```text
        ┌─────────┐
        │  FnOnce │  (Consumes `self`)
        └────┬────┘
             ▲
             │ supertrait of
        ┌────┴────┐
        │  FnMut  │  (Mutates `&mut self`)
        └────┬────┘
             ▲
             │ supertrait of
        ┌────┴────┐
        │   Fn    │  (Borrows `&self`)
        └─────────┘
```

### 1. `FnOnce`

- **Signature**: `fn call_once(self, args: Args) -> Output;`
- **Capability**: Consumes its environment (`self`).
- **Invocations**: Can only be called **at most once**.
- **Universal**: **All** Rust closures implement `FnOnce`.

### 2. `FnMut`

- **Signature**: `fn call_mut(&mut self, args: Args) -> Output;`
- **Capability**: Modifies its captured environment via a mutable reference.
- **Invocations**: Can be called multiple times.
- **Trait Relationship**: Any closure implementing `FnMut` also implements `FnOnce`.

### 3. `Fn`

- **Signature**: `fn call(&self, args: Args) -> Output;`
- **Capability**: Accesses its captured environment only via shared references `&self` (or captures nothing).
- **Invocations**: Can be called multiple times, concurrently from multiple threads.
- **Trait Relationship**: Any closure implementing `Fn` also implements `FnMut` and `FnOnce`.

### Trait Derivation Matrix

| Capture Method inside Body                       | Automatic Trait Implementations |
| :----------------------------------------------- | :------------------------------ |
| Moves a captured value out of the closure        | `FnOnce` only                   |
| Mutates a captured value                         | `FnMut` and `FnOnce`            |
| Only reads captured values (or captures nothing) | `Fn`, `FnMut`, and `FnOnce`     |

```rust
// Only FnOnce: moves `s` out of its environment
let s = String::from("hello");
let consume = || drop(s);
consume();
// consume(); // ERROR: use of moved value

// FnMut: mutates state
let mut n = 0;
let mut add = || n += 1;
add();
add();

// Fn: purely reads state
let pi = 3.14159;
let calc = |r: f64| pi * r * r;
let _a1 = calc(2.0);
let _a2 = calc(3.0);
```

## 8. Accepting Closures as Function Parameters

When writing functions that take closures, you have two design dimensions:

1. **Which trait to require (`Fn`, `FnMut`, or `FnOnce`)**
2. **Static dispatch vs. Dynamic dispatch**

### Choosing the Trait Bound

- Ask for **`FnOnce`** if your function calls the closure **once** (e.g., `Option::map`, `thread::spawn`).
- Ask for **`FnMut`** if your function calls the closure **multiple times and allows it to mutate state** (e.g., `Iterator::filter`, `Iterator::map`).
- Ask for **`Fn`** if your function calls the closure **multiple times without allowing it to mutate state**, or if you need to run it concurrently across threads.

### Approach A: Static Dispatch (Generics)

- **Performance**: Zero-cost abstraction. The compiler inlines the closure code.
- **Drawback**: Increases binary code size (monomorphization).

```rust
fn apply_twice<T, F>(mut func: F, val: T) -> T 
where
    F: FnMut(T) -> T,
    T: Copy,
{
    func(func(val))
}

let double = |x: i32| x * 2;
assert_eq!(apply_twice(double, 5), 20);
```

### Approach B: Dynamic Dispatch (Trait Objects)

- **Performance**: Small runtime overhead (vtable pointer indirection). Prevents inlining.
- **Benefit**: Allows homogenous collections of closures or reduces monomorphization bloat.

```rust
// Accepts a reference to a dynamically dispatched closure
fn execute_dynamic(f: &dyn Fn(i32) -> i32, val: i32) -> i32 {
    f(val)
}

let increment = |x| x + 1;
assert_eq!(execute_dynamic(&increment, 10), 11);
```

## 9. Returning Closures

Because each closure has a unique, anonymous type, you cannot write its concrete type directly in the return signature.

### Option 1: `impl Trait` (Static Dispatch)

Preferred for single concrete closures. The closure must own its captures (`move`).

```rust
fn make_adder(x: i32) -> impl Fn(i32) -> i32 {
    // Must use `move` so `x` is packed inside the returned struct
    move |y| x + y
}

let add_five = make_adder(5);
assert_eq!(add_five(10), 15);
```

*Limitation*: You cannot return two different closures with `impl Trait` from conditional branches, because their generated anonymous types differ:

```rust
// THIS WILL FAIL TO COMPILE:
// fn conditional_closure(flag: bool) -> impl Fn(i32) -> i32 {
//     if flag {
//         |x| x + 1
//     } else {
//         |x| x + 2 // ERROR: `if` and `else` have incompatible types
//     }
// }
```

### Option 2: `Box<dyn Trait>` (Dynamic Dispatch)

Heap-allocates the closure and erases its concrete type.

```rust
fn conditional_closure(flag: bool) -> Box<dyn Fn(i32) -> i32> {
    if flag {
        Box::new(|x| x + 1)
    } else {
        Box::new(|x| x + 2)
    }
}

let f = conditional_closure(false);
assert_eq!(f(10), 12);
```

## 10. Closures vs. Function Pointers (`fn`)

A function pointer is written with a lowercase `fn` (e.g., `fn(i32) -> i32`). It is a concrete pointer type, not a trait.

### Crucial Rule:

- **Any closure that captures NO variables from its environment can coerce to a function pointer `fn(...) -> ...`.**
- **Closures that capture variables CANNOT be passed where a `fn` is expected.**

```rust
fn execute_fn_pointer(func: fn(i32) -> i32, arg: i32) -> i32 {
    func(arg)
}

// 1. Regular function: OK
fn square(x: i32) -> i32 { x * x }
execute_fn_pointer(square, 4);

// 2. Closure with NO captures: OK (coerces to `fn`)
let no_capture = |x: i32| x * 2;
execute_fn_pointer(no_capture, 4);

// 3. Closure WITH captures: FAILS
let offset = 10;
let with_capture = |x: i32| x + offset;
// execute_fn_pointer(with_capture, 4); 
// ERROR: expected fn pointer, found closure
```

## 11. Advanced Patterns: Lifetimes, HRTBs, and Async

### 1. Higher-Rank Trait Bounds (HRTBs)

Sometimes a closure must accept a reference of *any* arbitrary lifetime, not just a specific one chosen by the caller.  
This is expressed using `for<'a>` syntax:

```rust
// Read: "F is a closure that, for ANY lifetime 'a, takes &'a str and returns usize"
fn process_text<F>(func: F) 
where
    F: for<'a> Fn(&'a str) -> usize,
{
    let s = String::from("transient");
    println!("Length: {}", func(&s));
}
```

The shorthand `F: Fn(&str) -> usize` automatically desugars to this HRTB.

### 2. Recursive Closures

Because closure types are unnameable and recursive types must have a known size, you cannot define a recursive closure directly:

```rust
// To achieve recursion, use a reference to a trait object:
let mut factorial: &dyn Fn(u32) -> u32;
let closure = |n: u32| -> u32 {
    if n <= 1 { 1 } else { n * factorial(n - 1) }
};
factorial = &closure;

assert_eq!(factorial(5), 120);
```

### 3. Async Closures (`async ||`)

In modern Rust (Rust 1.85+), async closures are first-class citizens:

```rust
// An async closure returns a future that borrows from the closure's state
let async_closure = async |x: i32| -> i32 {
    tokio::time::sleep(std::time::Duration::from_millis(10)).await;
    x * 2
};
```

These implement the `AsyncFn`, `AsyncFnMut`, and `AsyncFnOnce` traits, solving historical lending-borrow lifetime bugs when returning futures that borrow closure captures.

## 13. Quick Reference & Common Compiler Errors

### Trait Decision Flowchart

```text
Can the closure be called more than once?
  │
  ├── NO ──────────────────────────────────────────► FnOnce
  │
  └── YES
        │
        Does the closure mutate captured state?
        │
        ├── YES ───────────────────────────────────► FnMut
        │
        └── NO (Reads only or no captures) ────────► Fn
```

### Common Compiler Diagnostics & Solutions

#### 1. `E0507: cannot move out of ... in a closure`

- **Root Cause**: The closure implements `Fn` or `FnMut`, but its body attempts to take ownership of a captured reference.
- **Fix**: Either clone the data inside the body or accept that the closure can only be called once (`FnOnce`).

#### 2. `E0525: expected a closure that implements the 'Fn' trait, but it implements 'FnMut'`

- **Root Cause**: A function (like `Iterator::map`) or data structure expects `Fn`, but your closure modifies a local captured variable.
- **Fix**: Refactor state mutation into interior mutability (`Cell`/`RefCell`/`Mutex`) or verify if the receiver can accept `FnMut`.

#### 3. `E0373: closure may outlive the current function, but it borrows X`

- **Root Cause**: You are returning a closure or sending it across a thread boundary, but it borrows data from the current stack frame.
- **Fix**: Add the `move` keyword before the closure arguments: `move |...| { ... }`.

## 14. Callable Traits in Rust

Rust has three special traits that describe **how a value can be called like a function**:

```text
Fn
FnMut
FnOnce
```

They are primarily used with **closures**, but the underlying idea is broader: a type implementing one of these traits can be invoked using function-call syntax:

```rust
value(arg1, arg2)
```

### 1. `Fn`

`Fn` means: **The callable can be called repeatedly without mutating or consuming its captured environment.**

Signature:

```rust
Fn(Args) -> ReturnType
```

For example:

```rust
F: Fn(i32, i32) -> i32
```

means:

```text
F
 └── can be called with (i32, i32)
 └── returns i32
```

Example:

```rust
let add = |a, b| a + b;

add(10, 20);
add(30, 40);
```

The closure doesn't modify or consume anything from its environment, so it can implement `Fn`.

### 2. `FnMut`

`FnMut` means: **The callable may mutate its captured environment, so calling it requires mutable access.**

Signature:

```rust
FnMut(Args) -> ReturnType
```

Example:

```rust
let mut count = 0;

let mut increment = || {
    count += 1;
};

increment();
increment();
```

The closure modifies `count`, which it captured from the surrounding environment.  

Therefore it requires mutable access to the closure:

```rust
let mut increment = || {
    count += 1;
};

increment();
```

Notice:

```rust
let mut increment
```

The closure itself must be mutable because calling it mutably changes its captured state.

### 3. `FnOnce`

`FnOnce` means: **The callable may consume something from its captured environment, so it can potentially be called only once.**

Signature:

```rust
FnOnce(Args) -> ReturnType
```

Example:

```rust
let message = String::from("Hello");

let consume = || {
    drop(message);
};

consume();
```

The closure **moves/consumes** `message`.

After that, `message` is gone, and the closure cannot necessarily be called again.

### The relationship between them

The important part is that these traits form a hierarchy:

```text
FnOnce
  ↑
 FnMut
  ↑
  Fn
```

More precisely:

```text
Fn: FnMut: FnOnce
```

So:

```text
Every Fn closure is also FnMut and FnOnce
Every FnMut closure is also FnOnce
But not every FnOnce closure is FnMut
```

Think of the capabilities as becoming progressively more restrictive:

```text
Fn
│
├── Can call repeatedly
├── Doesn't mutate captured environment
└── Doesn't consume captured environment

FnMut
│
├── Can call repeatedly
├── May mutate captured environment
└── Doesn't consume captured environment

FnOnce
│
├── Can call at least once
└── May consume captured environment
```

### One important correction to the mental model

`Fn`, `FnMut`, and `FnOnce` **do not describe the arguments or return type by themselves**.

This:

```rust
Fn(i32, i32) -> i32
```

has two pieces:

```text
Fn
│
└── callable behavior

(i32, i32) -> i32
│              │
│              └── return type
└── arguments
```

So:

```rust
F: Fn(i32, i32) -> i32
```

means:

> `F` is a callable type that can be invoked with two `i32` arguments and returns an `i32`.
